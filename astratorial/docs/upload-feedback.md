# Upload and processing feedback

Choosing or recording a video starts the tutorial automatically. The screen now shows the current operation immediately: checking the connection, opening a private workspace, preparing the transfer, uploading bytes, confirming storage, and joining the processing queue. An unavailable connection explains the missing service and offers **Check connection** while retaining the selected video. There is no separate disabled analysis button.

The processing view follows saved worker stages: video preparation, understanding, planning, animation, narration/rendering, and validation. Queued jobs say they are waiting; failed and paused jobs stop showing an active animation message. Uploads show their actual byte count and percentage, including zero, with reconnection messages, pause/resume, and a timeout for stalled transfers.

JSON API requests have a 30-second timeout. Network errors, unreadable responses, guest-session failures and generation failures have readable explanations. Retry preserves an existing upload ticket or saved generation job. A timeout does not prove that the server stopped processing a request, so queue creation remains idempotent and polling continues after temporary failures.

`npm run worker` writes a local heartbeat under the ignored `.astratorial/` directory. `/api/runtime` reports whether the process is alive and whether its queue connection succeeded. This check is separate from configured credentials; the UI can explain why a saved video is waiting even when the website itself is online. It does not block uploads or expose process IDs, file paths or credentials.

For local startup, follow the [README](../README.md). After rebuilding, restart the website and worker and refresh open browser tabs so every process loads the new code. Other computers connected to the same project must also update their workers to produce the new detailed failure messages. The existing in-app browser had retained an older upload interface during this work; refreshing it loaded the current automatic flow.

Browser regressions cover slow configuration, connection recovery, guest-session failure, delayed upload authorization/transfer/confirmation, a stopped worker, and generation retry without duplicate upload or enqueue. Unit tests cover client timeout and cancellation, worker heartbeat freshness, safe failure messages, and rendering retries that reuse completed assets without new model or narration requests.

Real browser testing found two blockers that mocked upload tests did not expose. The server now accepts the explicitly configured `NEXT_PUBLIC_APP_URL` when its bind address differs from the browser origin, while continuing to reject unrelated origins and forged forwarding headers. Signed storage uploads now use `/storage/v1/upload/resumable/sign` with the short-lived upload signature and public project key. The ordinary TUS endpoint requires a user JWT and rejected the previous requests before any bytes reached parsing. This matches Supabase's [signed resumable upload example](https://github.com/supabase/supabase/blob/master/examples/storage/resumable-upload-signed-uppy/index.html). Both fixes have regression coverage.

Verification on September 10, 2026: all 87 unit tests, TypeScript, ESLint, and the production build passed. All 24 upload-feedback browser cases passed against the rebuilt production server on desktop and mobile viewports. The existing 34 guest, upload, recorder, player, scene, and practice browser cases passed during the coordinated changes. A real browser upload reached private Supabase storage, completed upload confirmation, queued generation, and displayed a worker failure for an intentionally malformed video. Its budget recorded $0 spent and $0 reserved; disposable files, tutorial, and guest identity were removed. The updated local worker's decode-error message was also verified. Browser tests cover interface behavior, not physical-device performance or successful AI tutorial generation.
